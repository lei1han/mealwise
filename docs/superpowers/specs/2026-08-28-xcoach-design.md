## 1. 产品概述

### 1.1 一句话定位

**三餐教练** 是一个以微信小程序形态呈现的减肥教练，人格"亦师亦友 + 一点毒舌"，通过聊天帮助**屡减屡败、有基础但缺监督的减肥人群**"靠谱地瘦下来"。

### 1.2 产品要解决的问题

这个人群的特点：**有减肥基础、却屡次失败**。核心痛点不在"不懂"，而在"做不到"：

1. **方法知道、执行不了**：懂热量、会算，但一个人坚持不下来，屡次半途而废、反弹。
2. **缺监督与陪伴**：听够了道理，缺一个真正"盯"着他们、在崩溃边缘拉一把的人。

三餐教练用"聊天"这种最低门槛的形式，负责**把用户早就知道的方法真正执行到底**——不重复教基础，而是监督、戳破自欺、在关键时刻兜底。

### 1.3 产品价值主张

- **核心价值**：靠谱减重结果。
- **底色**：伙伴式的陪伴（情绪支持、监督、鼓励）。

## 2. 核心对话闭环

每天的主线节奏（教练作为对话的发起与推动者）：

1. **早上**：主动问候 + 催报体重/状态。
2. **三餐 + 加餐**：主动追问"中午吃什么了？"，用户用"半拳 / 一拳 / 两拳"等模糊量词描述分量 → 教练返回**热量区间 + 一句建议 + 对比今日预算**。
3. **晚上**：总结今日热量、体重趋势、明天的小目标。
4. **随时**：可聊心情、计划、期望（伙伴身份兜底）。
5. **失联 / 漏报**：毒舌提醒一下，但不伤自尊。

### 2.1 典型对话示例

> 用户：中午吃了半拳米饭、一拳青菜、半拳鸡腿肉。
> 三餐教练：这餐大概 320~400 大卡，鸡腿肉选得不错，蛋白质够了；米饭半拳刚刚好。今天早餐 280，加上这顿，离预算还剩约 600，下午别点奶茶了啊。

> 用户：今天心情不好，特别想吃甜的。
> 三餐教练：先抱一个。想暴食说明今天热量缺口拉太猛了。给你两个选：下午加个一拳的水果，或者晚上主食减半换一块 85% 黑巧。告诉我你选哪个，别自己硬扛。

## 3. 教练人设与语气规范

### 3.1 人设

- **专业教练面**：给数据、给计划、客观指出问题，有理有据。
- **伙伴面**：能共情、能陪聊心情与期望，不居高临下。
- **毒舌面**：轻损一句 + 随即给台阶，损事不损人，绝不身体羞辱。
- **对用户的默认态度**：他们大多有基础、屡战屡败，教练不重复讲基础道理，重点是监督执行、戳破自欺、在情绪崩溃时兜住。

### 3.2 毒舌尺度（轻损 + 可调）

- **轻损原则**：针对"行为"吐槽，不针对"人"；损完必须接一句建设性的鼓励或台阶。
- **禁止**：攻击外貌、身体羞辱、制造身材焦虑、羞辱饮食习惯。
- **可调**：初次对话询问用户耐受度，分三档，可随时切换：
  - 温柔：几乎不损，鼓励为主。
  - 轻损（默认）：损一句 + 给台阶。
  - 辛辣：损得更狠，但仍然有度、不越界。

### 3.3 语气硬约束

- 模糊量词体系：分量统一用"半拳 / 一拳 / 两拳（以上）"描述，不要求用户上秤。
- 热量统一输出为**区间值**，不输出看似精确的虚假数字。
- 所有建议必须可执行、当日可落地，不给空泛的"少吃多动"。

## 4. 热量估算机制（方案 C）

### 4.1 分层结构

- **底座（可控）**：内置常见食物库，每项食物维护"1 拳 / 1 份"的基准热量与误差区间（如 "1 拳米饭 ≈ 120 千卡，区间 ±15%"）。
- **换算规则**：半拳 = 0.5×，一拳 = 1×，两拳 = 2×，两拳以上按 2.5× 并提示。
- **LLM 兜底（灵活）**：负责理解自然语言、把描述归类到库内食物；库外 / 复合菜（如"红烧肉盖浇饭"）用经验区间估算并诚实标注"估算"。

### 4.2 输出格式规范

- 统一格式：`这餐约 {min}~{max} 大卡`，并附一句当日预算对比。
- 当估算置信度低时，主动说明"这个我拿不太准，粗略估是 X~Y"。

### 4.3 食物库维护（MVP 阶段）

- MVP 只维护高频核心食物（主食类、蛋白类、肉禽水产蛋、蔬菜、水果、常见外卖/零食），约 50~100 项。
- 后续迭代扩充条目，并支持用户自定义食物。

## 5. 目标机制（渐进式定标）

分四阶段：

1. **摸底**：性别、年龄段、身高、当前体重、过往减肥史（几次失败、为什么反弹）、饮食、运动、作息、减肥动机、期望与限制。
   - 性别与年龄段用于热量预算与定标公式的科学计算（BMR/TDEE），首次对话中自然带出，不作敏感盘问。
2. **定标**：倒推一个**现实目标**（健康区间约每周减 0.3~0.75 kg），给出目标体重 + 预估周期，并让用户确认。
3. **执行**：每日热量预算 + 每日可执行行动建议，随体重反馈动态微调。
4. **收敛 / 重整**：遇到平台期或目标变化时，重新校准目标，不硬逼。

教练的核心动作是：**从用户的现状出发，倒推一个她"够得着且愿意信"的目标，再逐步收紧。**

## 6. 技术架构

### 6.1 总体示意

```
微信小程序（前端，纯对话）
        │
        ▼
后端服务（网关 + 业务逻辑 + 记忆读写）
        │
        ├── AI 模型 API（LLM：承载人设 + 换算 + 兜底 + 生成建议）
        ├── 简易数据库（用户信息、记忆点、体重/饮食记录）
        └── 定时任务 / 订阅消息（主动督促）
```

### 6.2 各层职责

- **前端（微信小程序）**：聊天气泡 + 极简输入，MVP 不做复杂可视化；只负责收/发与订阅消息授权。
- **AI 模型 API**：通过系统提示词固化人设、拳换算规则、区间输出格式、毒舌尺度；通过结构化输出把"饮食记录、记忆点"回写给后端。
- **数据库**：见第 7 节数据模型。
- **主动督促**：借助微信"订阅消息 / 服务通知"实现定时推送；用户需一次性授权，漏报时按既定策略催报。

> 平台约束：微信小程序无法像原生 App 那样后台任意推送，主动督促依赖订阅消息，MVP 阶段需接受"授权 + 有限频次"的限制。

## 7. 数据模型（记忆点）

### 7.1 users（用户）

| 字段 | 说明 |
|---|---|
| id | 用户唯一标识 |
| nickname | 昵称 |
| gender | 性别（male / female） |
| age_group | 年龄段（18-24 / 25-34 / 35-44 / 45-54 / 55+） |
| height | 身高 |
| initial_weight | 初始体重 |
| target_weight | 目标体重 |
| estimate_weeks | 预估周期 |
| daily_calorie_budget | 每日热量预算 |
| snark_level | 毒舌档位（温柔/轻损/辛辣） |
| food_restrictions | 饮食禁忌 / 过敏 |
| dietary_preferences | 饮食偏好 |
| exercise_condition | 运动条件 |
| exercise_habits | 运动习惯 |
| motivation | 减肥动机 |
| created_at | 创建时间 |

### 7.2 memories（关键记忆点）

| 字段 | 说明 |
|---|---|
| id | 记忆点唯一标识 |
| user_id | 所属用户 |
| category | 类型：static / dynamic / emotion |
| content | 记忆内容 |
| created_at | 记录时间 |

- **static**：性别、年龄段、身高、初始体重、目标、减肥史、禁忌、饮食偏好、运动条件、运动习惯、动机等。
- **dynamic**：每日体重、每日饮食与热量区间、每日预算、当前小目标。
- **emotion**：心情节点、容易破防的时刻、喜欢的鼓励方式、毒舌耐受度。

### 7.3 weight_records / diet_records（行为记录）

- **weight_records**：user_id、日期、体重。
- **diet_records**：user_id、日期、餐次、原始描述、热量区间 min / max、是否已汇总。

### 7.4 扩展集合（后端工程 / 商业埋点侧）

本节仅保留"核心 4 表"的产品级视图；实际工程落地还依赖以下扩展集合，具体 schema 以后端计划 `2026-08-28-xcoach-backend.md` §4 为冻结版：

- `messages`：聊天历史，用于会话编排与上下文裁剪。
- `subscribe_quotas`：订阅消息剩余可发送额度，支撑主动督促的触达额度管理。
- `subscribe_auth` / `notify_log`：订阅授权状态与触达日志，由**契约 A 增量提案**（商业埋点）提出，当前待后端冻结确认表结构。

> 各记录表（weight_records / diet_records、含 subscribe_auth / notify_log）需带精确时间戳（created_at 等），否则「留存 / 流失 / 主动督促有效性」三类指标不可算，详见契约 A 增量提案 §2。

## 9. 成功指标

北极星 = **靠谱减重结果**，落到可量化指标：

- **北极星指标**：达成目标体重的用户比例 / 平均减重达成度。
- **健康过程指标**：日均汇报次数、连续汇报天数（留存）、热量汇报覆盖率、阶段小目标达成数。
- **负向监控**：用户情绪低谷与流失节点（用于反哺陪伴策略）。

---

## 10. 风险与开放问题

1. **订阅消息频次受限**：主动督促能否达到"盯人"的效果，需在 MVP 阶段验证。
2. **热量估算的公信力**：区间值 + 诚实标注"估算"是可信度的关键，需监控用户对数字的信任度。
3. **毒舌的边界**：轻损 + 可调是护栏，但需要对话级的内容安全兜底（禁止身体羞辱）。
4. **数据隐私**：体重、饮食、情绪属于敏感信息，需明确存储与使用边界。
